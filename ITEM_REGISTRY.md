# Реестр предметов Valheim — PASS 2

Проверка от 17 октября 2026 года: установленная Valheim **1.0.20**, статический сериализованный `ObjectDB` из игровых файлов. Зарегистрировано **1519 определений из 1522 ссылок ObjectDB — 99,80%**. Это проверенный результат локального извлечения, `scope=installed-assets`, `runtimeVerified=false`, `complete=false`.

Каталог включает внутренние `ItemDrop` атак NPC и других служебных объектов. Поэтому число 1519 нельзя трактовать как количество добываемых игроком ресурсов. Полнота текущего реестра работающей игры, включая изменения модов, пока не подтверждена.

## Автоматическое построение

Первый источник — [ValheimIconExporter](tools/ValheimIconExporter/export_items.py). Инструмент читает установленные Unity assets и AssetBundles, находит сериализованный ObjectDB, разрешает его ссылки на `ItemDrop` и читает `m_itemData.m_shared`. Для игровых типов используются type trees, полученные из локально установленной сборки. RU/EN читаются из настоящих таблиц локализации. Файлы игры и сохранения не изменяются.

Пример запуска из корня проекта в PowerShell:

```powershell
py -3 -m venv .runtime/registry-python
.runtime/registry-python/Scripts/python.exe -m pip install -r tools/ValheimIconExporter/requirements.txt
.runtime/registry-python/Scripts/python.exe tools/ValheimIconExporter/export_items.py --game "<папка Valheim>" --game-version "1.0.20" --output localdata
```

Замените папку и версию на свою установленную игру. Версия Unity сохраняется отдельно в `source.assetFormat`; её нельзя выдавать за версию Valheim. При отсутствии надёжного источника версии параметр можно опустить: останется `UNKNOWN`.

Результаты находятся только локально:

- `localdata/registry/items.json` — манифест определений и источников.
- `localdata/registry/extraction-report.json` — счётчики, пропущенные ссылки, конфликты локализации и ошибки извлечения.
- `localdata/icons/<sha256>.png` — полученные из игры изображения.
- `localdata/registry/overrides.json` — отдельные локальные переопределения категорий.

Backend отслеживает изменение манифеста без перезапуска панели. Некорректный новый манифест не заменяет последний исправный каталог; ошибка видна в `registry.loadError`.

Второй источник — [runtime-экспортёр C#](plugin/RegistryExporter.cs), [описание](tools/registry-runtime/README.md). После обычной загрузки обновлённого BepInEx-плагина он читает текущий `ObjectDB.instance.m_items`, извлекает определения и Sprite, отправляет PNG и затем манифест в локальный API. Новые определения и неизвестные предметы инициируют безопасную повторную индексацию. Принудительное подключение DLL к уже работающему процессу не используется. Выполнение нового экспортёра в реальном игровом процессе остаётся отдельной непроверенной интеграцией.

## Идентичность и количество

Основной ID — **`prefab:<точное имя prefab>`**. Отображаемые названия, локализация, категория и изображение не участвуют в идентификации. Одноимённые предметы разных prefab остаются отдельными.

Запись каталога содержит `id`, `prefab`, signed 32-bit `prefabHash`, `nameRu`, `nameEn`, `category`, `subcategory`, `maxStack`, `iconKey`, `source`, `metadata`, `diagnostics`. Метаданные сохраняют доступные сведения `ItemType`, качество, варианты, вес, пищевые значения, телепортацию, квестовый признак и исходные ключи локализации. Источник конкретного мода без надёжных данных остаётся `UNKNOWN`.

Нативный `GetStableHashCode` используется только как дополнительный индекс. Сохранённый `hash:<signed decimal>` разрешается, только если найден ровно один prefab с таким hash. При коллизии точные prefab сохраняются, неоднозначный hash остаётся неизвестным с диагностикой. Дубли `id` и несовпадение переданного hash с точным именем prefab отклоняют манифест целиком.

Исходные токены и количества сохранённого инвентаря не переписываются при загрузке каталога. Нормализация происходит при чтении состояния. Если в одном сундуке есть точный prefab и соответствующий ему hash, их текущие стеки суммируются один раз. История сообщений не прибавляется к текущим остаткам. Перенос между сундуками сохраняет общий итог; новая наблюдаемая опись заменяет предыдущую опись того же контейнера.

Поля `quality`, `variant`, `modId`, `customData` и instance `metadata`, если переданы источником, сохраняются в `variants[]` с количеством. Общая строка ресурса по prefab не теряет эти различия. Список `sourceIds` сохраняет исходные идентификаторы; поиск учитывает RU, EN, точное имя prefab, внутренний ID и исходные hash-псевдонимы. Необычная нулевая или отрицательная нативная вместимость стопки представляется как `maxStack:null`, `metadata.rawMaxStack` и `INVALID MAX STACK`, без выдуманного значения.

Неизвестный предмет остаётся в группе `Неопознанные` с исходным ID, названием и количеством. Ответ ingest содержит `reindexRequested:true`; плагин дополнительно проверяет изменение текущего ObjectDB. Ошибка реестра не должна останавливать отдельную синхронизацию контейнеров.

## Категории и диагностика

В [backend](server/registry.mjs) задано 18 категорий: древесина и растения; камень и минералы; руды и металлы; строительные материалы; сельское хозяйство; сырые продукты; приготовленная еда; ингредиенты; трофеи; кожа, кости и ткани; оружие; броня; инструменты; боеприпасы; зелья и расходники; ценные предметы; ключевые и специальные предметы; прочее.

Классификатор использует точный `ItemType` установленной версии, имя prefab и доступные свойства: пищевые значения, `isDrink`, `questItem`, стоимость и наличие build pieces. Непонятное определение получает `Прочее` и `CATEGORY UNRESOLVED`; это явная диагностическая категория. Автоматическая категория может требовать ручного уточнения.

`PUT /api/registry/overrides` с `{prefab,category,subcategory?}` сохраняет только локальное отображение. `category:null` удаляет переопределение. Игровые определения, предметы и сохранения этим API не изменяются.

Основные диагностические состояния: `UNKNOWN ITEM`, `MISSING LOCALIZATION`, `MISSING ICON`, `DUPLICATE ID`, `HASH COLLISION`, `CATEGORY UNRESOLVED`, `INVALID MAX STACK`. Исходные уточняющие сообщения экспортёров также сохраняются.

## API, проверки и ограничения

`GET /api/registry` возвращает манифест, определения и сводку покрытия. `GET /api/state` обогащает реальные остатки каталогом и включает текущие счётчики неизвестных предметов. Загрузка реестра и PNG требует закрытый локальный `X-VRM-Token`; чтение доступно только через сервер, привязанный к loopback, с проверкой Host/Origin. Токен, пути установки, имена миров и игроков в публичный репозиторий не входят. Подробный контракт: [shared/contract.md](shared/contract.md).

[Регрессионные проверки реестра](server/registry.test.mjs) используют явно синтетические определения и инвентари: 2048 записей, RU/EN/ID/hash, настоящую коллизию алгоритма, качество/варианты, сохранение количества, смену каталога по WebSocket, неизвестные предметы, локальные переопределения и безопасность PNG API. Эти тесты проверяют алгоритмы и протокол. Они не являются игровым live-тестом. Реальная read-only сверка выше выполнена отдельно от синтетических тестов.

Остаются непроверенными: загрузка нового runtime-экспортёра в работающем Valheim после следующего обычного запуска, определения модов текущей сессии, GPU-экспорт внутри Unity и live-сценарий изменения стека в сундуке. Охват контейнеров мира остаётся частичным независимо от покрытия каталога. Система резервирования не реализована: `availableQuantity=quantity`, `reservedQuantity=0`, `reservationsImplemented=false`.

Защищённые игровые PNG, извлечённые определения, игровые DLL, сохранения, реальные SQLite и приватные отчёты исключены из Git. Публичный репозиторий содержит исходный код, контракт и инструкции для самостоятельного локального воспроизведения.
