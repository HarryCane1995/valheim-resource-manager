# Результаты тестирования MVP 0.1.0

Дата локальных проверок: **17.10.2026**. Этот отчёт отделяет реальные файловые/программные проверки от синтетических сценариев и неподтверждённого игрового runtime. Сохранения, рабочие базы, локальные журналы, координаты, идентификаторы мира/игроков и исходные скриншоты с реальными данными не опубликованы. Приватные наблюдения ниже пересказаны без их идентифицирующих данных; сторонний аудитор может воспроизвести публичные тесты на fixtures и выполнить игровой тест на своей установке.

## 1. Реальные проверки файлов и приложения

### Парсер настоящего завершённого сохранения

Прочитаны **114** mapping-чанков и **1 410 357 ZDO**. Counts каждого чанка и общий итог совпали с mapping; `.fwl2` разобран до конца; входные файлы повторно проверены SHA256 и не изменились во время чтения. Игровые файлы открывались только для чтения.

Распознаны **151** стационарный сундук четырёх snapshot-prefab и **21 233** единицы, **269** различных prefab/хешей. **202 типа / 6 469 единиц** остались неизвестными по prefab-хешу и не заменены предположениями. Ещё **2 352** объекта с inventory blob вне распознанного snapshot-каталога не включены в остатки; их назначение не установлено. Охват — **PARTIAL**.

Проверено совпадение примеров предметов между parser payload, SQLite API и карточками UI, включая количества, список мест хранения и координаты. Все 151 записи отображались как `SNAPSHOT`; настоящий runtime ZDOID не выдумывался. С осмотром тех же сундуков внутри игры данные **не сравнивались**. Это реальное чтение сохранения и проверка программной обработки, не live-игровой тест.

### Frontend в браузере

Production UI проверен в видимом Chromium при **1366×768** и **1920×1080**. В финальном состоянии не обнаружены горизонтальное переполнение и необработанные JS-ошибки; favicon возвращал 200. На настоящем snapshot проверены поиск, карточка ресурса, места хранения, координаты, время сохранения, статусы и обозначение частичного охвата.

Запоздавшие fetch ограничены scope/generation и отменой запросов: ответ прежнего demo/world/zone не должен попадать под новый заголовок источника. Проверено приложение после остановки/запуска собственных backend/watcher; SQLite сохраняла данные. Эти проверки подтверждают локальный UI и persistence, а не работу игрового сборщика.

При дополнительной проверке был обнаружен отказ dev proxy: POST с Origin `http://127.0.0.1:5173` получал `403 ORIGIN_REJECTED` до валидации/записи. Ошибка исправлена в proxy для HTTP и WebSocket без изменения строгой политики backend; отдельный тест описан ниже. Production-панель на `37841` продолжает использовать собственный допустимый origin.

### C# build и локальная установка

Исследованы Valheim **1.0.20**, BepInEx **5.4.23.5**, Harmony и Unity Mono references локальной установки. .NET SDK **9.0.200**, target `netstandard2.1`. Результат сборки — **0 ошибок**, два известных `MSB3277` предупреждения Unity facade для `System.Net.Http` / `System.IO.Compression`. Предупреждения не скрыты; возможное влияние на runtime требует игрового теста.

В локальном статическом IL-аудите проверены **258** прямых compiled call references; запрещённых вызовов изменения игровых данных не обнаружено. Это ограниченная статическая проверка, не полное доказательство отсутствия всех побочных эффектов и не тест API в процессе игры. Локальные инструменты, декомпиляции и игровые DLL в публичную поставку не включены.

Установка добавила только собственные DLL/CFG, с baseline их отсутствия и квитанцией отката. Сравнение хешей **242** ранее существовавших файлов core/модов/конфигураций показало **0 изменений**. Текущая сессия игры не прерывалась и новую DLL ещё не загрузила. Проверка установленного файла не заменяет проверку BepInEx runtime.

## 2. Автоматические тесты и симуляции

### 26 Node-тестов

Тесты выполняют **настоящий** backend, SQLite, HTTP и WebSocket, но подают **синтетические** игровые payload. Покрыты:

- Суммирование стеков, замена inventory, изъятие, перенос с сохранением общего количества.
- Подтверждённое уничтожение, повторное обнаружение, выгрузка без удаления, повторная индексация без накопления истории.
- Изоляция миров, строковые большие ZDOID, сохранение меток после повторного открытия SQLite.
- Timeout, отключение, восстановление, запрет омоложения старого сундука одним heartbeat.
- Круговые X/Z-зоны, минимумы и ресурсы с нулевым известным количеством.
- Смена runtime ID после перезапуска, стабильная идентичность, конфликт/откат целого пакета.
- Устаревшие сеансы и destruction IDs, порядок пакетов, точный повтор, различающееся тело с тем же sequence.
- Будущие и запоздалые timestamps, snapshot → live без дублей, защита свежего live от старого snapshot.
- Токен, Host/Origin, JSON/content-type/body limit, изоляция demo и WebSocket-обновления.
- Настоящие Vite proxy и backend на временных портах с отдельной тестовой SQLite: точный собственный loopback Origin/Host проходит HTTP и WebSocket; посторонний Origin, несовпадение `localhost`/`127.0.0.1`, чужой Host, порт 65536 и Host без порта получают `403`. HTTP использует намеренно неверный JSON: допустимый Origin достигает parser и получает `400 INVALID_JSON`, не изменяя данные. Допустимый WebSocket получает уведомление `state-changed`; посторонний Origin отклоняется. Проверена пустая реальная тестовая база после запросов.

Эти тесты подтверждают правила обработки данных. Они не вызывают `Inventory.m_onChanged` настоящей игры.

### 18 Python-тестов

Fixtures строят бинарные packages с inventory **108–110**, chunk **40–42**, optional fields, обеими малыми кодировками вращения, малыми координатами и ZDO-словарями. Проверены точные биты float32, int64 UID, неизвестные хеши с сохранением количества, число объектов mapping, metadata до конца и неизменность source bytes/mtime.

Отрицательные сценарии: неподдерживаемая версия, усечение, лишние хвостовые bytes, неверные counts, нечисловые/бесконечные координаты, reserved flags, неоднозначные сундуки/mapping, недостающее завершённое поколение. Это синтетическая проверка декодера; отдельно выполнено чтение настоящего snapshot из раздела 1.

### 11 PowerShell-тестов

Изолированные fixtures используют временные mock-каталоги игры/проекта. Собственная DLL и исследованная игровая DLL копируются в них; игровая DLL только читается, фиктивные loader и save sentinel не исполняются. Проверены:

- Добавление собственных файлов, повторная установка без изменения, проверенный откат.
- Отказ перезаписать существующие чужие DLL/CFG и сохранение других модов.
- Сохранение изменённого пользователем CFG/DLL и возможность закончить откат после восстановления оригинала.
- Отказ при подмене target path, game root, hash или независимой квитанции manifest.
- Отказ на несовместимой игровой DLL и на junction/reparse path.

Записи/удаления этих тестов направлены только в проверенный временный root. Они подтверждают file-operation guards, а не загрузку плагина игровым BepInEx.

### Синтетическое демо через браузер

Через явно помеченный demo UI проверены +40 дерева, перенос между сундуками с сохранением общего итога, отключение/сохранение остатков/восстановление, поиск и таблица, minimum, локальная метка и зона. Внешнее по отношению к UI mutation handler HTTP-действие изменило demo; браузер получил результат без ручного refresh в пределах **4 секунд** — допуска этого теста. Это время относится к demo/backend/UI, **не к игровой задержке**.

После demo-проверок настоящая база сохранила исходные 151 контейнер и 21 233 единицы. Демо выключено перед локальной передачей. Дополнительно проверены 78 известных русских prefab-названий; неизвестные модовые имена/хеши и количества сохранялись без угадывания.

## 3. Воспроизведение публичных проверок

Из корня свежего клона с Node.js 24+ и Python 3.11+:

```powershell
npm.cmd ci
npm.cmd run build
npm.cmd test
python -m unittest discover -s scripts -p "test_snapshot.py" -v
```

Собрать C# можно только с локально установленными game/BepInEx references:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\plugin\build.ps1 -GameDirectory "C:\Program Files (x86)\Steam\steamapps\common\Valheim"
```

После этого installer tests требуют исследованную игровую DLL с ожидаемым SHA256:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test_install.ps1 -AuditedAssemblyPath "C:\Program Files (x86)\Steam\steamapps\common\Valheim\valheim_Data\Managed\assembly_valheim.dll"
```

Без собственных игровых references возможно воспроизвести Node/Python/build проверки панели, но не C# build и installer tests. Реальные приватные snapshot/UI доказательства независимо не воспроизводятся из публичного клона; для повторения нужно своё поддерживаемое сохранение. Настройка snapshot и штатная установка описаны в [README.md](README.md).

## 4. Неподтверждённые сценарии и известные ограничения

| Сценарий/ограничение | Статус |
|---|---|
| Загрузка DLL и выполнение exporter в настоящем игровом процессе | UNVERIFIED |
| «40 дерева в настоящий сундук → +40 и правильное место в панели» | UNVERIFIED |
| Целевая задержка 1–2 секунды | Не измерена в игре |
| Настоящее изъятие, перенос, уничтожение, выход из области и повторный вход | Проверена логика на fixtures/demo; в игре UNVERIFIED |
| Совместимость с установленными модами и dedicated server runtime | UNVERIFIED |
| Переход watcher на новое реальное завершённое поколение | Ещё не наблюдался после его запуска |
| Полный охват мира/базы | Не подтверждается; collector сообщает PARTIAL |
| Snapshot prefab whitelist и неизвестные item hashes | Ограниченный каталог, точные количества сохраняются |
| Перемещение/замена сундуков с ключом по prefab + точной позиции | Ограничение идентичности; возможна новая запись/совпадение |
| Огромный мир/большой пакет/постоянный HTTP-отказ | Нет load/SLA proof; отказанный пакет может блокировать очередь |
| Будущие игровые версии и форматы | Экспорт/разбор отклоняются до нового аудита |
| Планирование крафта, удалённый multi-user доступ | В MVP не реализованы |

## 5. Следующая ручная приёмка в игре

При следующем обычном запуске игры с работающим backend:

1. Подтвердить загрузку плагина по локальному BepInEx-журналу и активному источнику панели.
2. Задать правильную складскую зону и записать исходный остаток дерева.
3. Положить ровно 40 дерева, сверить +40, сундук/XYZ и измерить фактическое время до UI.
4. Забрать предметы и перенести между двумя учтёнными сундуками; сверить итог после обоих подтверждений.
5. Уйти с базы, проверить сохранение последних остатков и честный статус; вернуться и подтвердить обновление.
6. Проверить настоящее уничтожение тестового пустого сундука и новый завершённый save → watcher цикл отдельно от live.

До выполнения и фиксации этих действий статусы `UNVERIFIED` нельзя заменять на PASS на основании сборки, демо или наличия файлов.
