# Local API contract

Minimum defaults and stock display:

- `PUT /api/minimums/default` with `{worldId, minimum, resetOverrides?: boolean}` sets a persistent per-world integer minimum (0–1,000,000,000). `resetOverrides:true` atomically clears individual minima. A new world defaults to 0 until configured. The requested working world uses 200.
- State includes numeric `defaultMinimum`. Each resource's `minimum` is its individual override, including explicit 0, or this default. Existing individual `PUT /api/minimums` remains supported.
- An observed-item watch set retains genuinely seen resources after depletion/destruction at zero when their effective minimum is positive. It is seeded from recorded container inventories and deliberate individual minima, never the entire registry. Future observed items inherit the default. Scopes change quantities; thresholds/watch set belong to the world. An absent item with an explicit minimum of 0 is hidden. A host bed reported as unset still pauses all accounting and zero rows.
- Stock level is deficit below minimum, near from minimum to less than 125%, surplus at 125% or higher. Thus a 200 minimum means red 0–199, yellow 200–249, green 250+. The meter marks the minimum at 80% of its range, keeps actual quantities in accessible text and stays neutral for disabled/invalid minima. Source freshness remains a separate status.

Node 24 backend listens only at `http://127.0.0.1:37841`; production assets are served from `dist/`.

- `GET /api/state?demo=0|1&worldId=<id>&zoneId=all|<id>` returns the selected database state. Omitting world selects the first world. Omitting zone is `all`.
- `POST /api/ingest` requires `X-VRM-Token` (private local file `data/ingest-token.txt`) and JSON `{sourceId,worldId,worldName,mode:'client'|'host'|'server'|'snapshot',sessionId,sequence,containers:[{id,identityKey?,type,name,x,y,z,items:[{prefab,name,category?,quantity}],observedAt}],destroyedIds:[],coverage:'partial'|'authoritative',gameVersion}`. Empty `containers` is a heartbeat. Sequence increases within a world/source/session; exact retry of its last accepted payload returns 200 without changing revision or freshness. Reused sequence with different body, an older sequence, or a retired session returns 409. Timestamp accepts ISO 8601 or epoch milliseconds; future timestamps are capped to receipt time. Entries older than a newer existing observation are ignored. Ingest always targets the real database.
- `POST /api/snapshot` uses the same authentication/body and requires `mode:'snapshot'`, `coverage:'partial'`. It records genuine parsed save observations without claiming a game connection. No omitted container is deleted. A newer live observation replaces the same stable identity.
- `POST /api/containers/<encoded id>/label?demo=0|1` body `{worldId,label}`.
- `PUT /api/minimums?demo=0|1` body `{worldId,prefab,minimum}`.
- `POST /api/zones?demo=0|1` body `{worldId,name,x,z,radius,enabled}`.
- `PUT /api/zones/<id>?demo=0|1` body `{worldId,name,x,z,radius,enabled}`.
- `POST /api/demo/start` explicitly creates or resets synthetic demonstration data in `data/demo.sqlite` only.
- `POST /api/demo/step` body `{action:'add40'|'move'|'disconnect'|'reconnect'}` changes the explicit demo fixture. `add40` adds 40 wood to the main chest; `move` transfers up to 20 wood to the forge chest. Demo stays disconnected until reconnect.
- `GET /api/health` gives application health, no credentials.
- `/ws` emits `{type:'state-changed',revision,demo}` on updates and clock/status changes. Refetch state. No inventory/token in WebSocket messages.

All label/minimum/zone/demo mutations return the complete selected-world state (with all zones); invalid requests return `{error,code}` with 4xx. JSON mutations require `Content-Type: application/json`. Same-origin browser mutations only. CLI ingest needs its token. Host header must be localhost or 127.0.0.1 and the server's port. No CORS access from unrelated web origins.

State shape: `{demo,worlds:[{id,name}],world:{id,name}|null,source:{connected,mode,coverage,scope,lastSeenAt,lastConfirmedAt,gameVersion},containers:[{id,zdoId,identityKey,type,name,label,x,y,z,items:[{prefab,name,category,quantity}],observedAt,status:'LIVE'|'STALE'|'OFFLINE'|'SNAPSHOT',zoneIds:[]}],resources:[{prefab,name,category,quantity,containerIds:[],minimum,status}],zones:[{id,name,x,z,radius,enabled,proposed}],minimums:{[prefab]:number},events:[{id,at,text}],stats:{totalItems,uniqueItems,containers,shortages},revision}`.

`observedAt`, `lastSeenAt` and `lastConfirmedAt` are ISO timestamps. `lastSeenAt` is heartbeat receipt; `lastConfirmedAt` is the latest actual observation of any retained container in the selected world and is the appropriate UI inventory-update time. A source becomes disconnected after 12 seconds without heartbeat. LIVE requires an observation within 15 seconds as well as an active source and matching current session; a heartbeat alone cannot refresh a container. Loaded-container periodic reconciliation must refresh the observation itself. Older confirmed entries are STALE; disconnected source entries are OFFLINE. Genuine snapshot observations remain SNAPSHOT independently of heartbeat and have `zdoId:null` because runtime identity is unavailable. Snapshot imports cannot replace a recent actively confirmed live entry, including equal timestamps. Only explicit `destroyedIds` delete inventory; unloaded or omitted containers persist. All quantities are current per-container sums, never accumulated across historical messages. If multiple sources are present, source status reflects an active host/server preferentially, then active client, then latest source; per-container status uses its own source.

Valheim 1.0.20 does not persist runtime ZDOIDs in the parsed chunk-42 save layout. Stable stationary-container identity is `pos-v1:<signed decimal prefabHash>:<x float32 bits hex8>:<y bits>:<z bits>`. With an identityKey, `state.id` is `stable:<identityKey>` (use this ID in label API and React keys), and `state.zdoId` is the latest exact runtime ZDO string, or an explicitly snapshot-prefixed ID. Labels and minima survive live reconciliation after restart. Never coerce ZDOIDs to JS numbers. Duplicate identities or conflicting positions fail closed, rolling back the complete packet. Destruction IDs resolve only against a matching source/current session; a recycled ID cannot delete an old session's unrelated container. Moving containers are excluded by the collector. The legacy no-identity path exists for API fixtures; the integration should always supply stable identity.

Resource `status` is the least current contributing container status. Shortage = minimum > quantity; minimum-only resources are included at zero. A new world has default minimum 0 until explicitly configured; an individual minimum overrides it, including 0. The first actual observation creates an editable `Основная база` zone centered at that observation with radius 100 m and `proposed:true`; it is an initial location suggestion, not a claim of complete base coverage. Saving zone coordinates clears `proposed`. `zoneId=all` counts known containers within any active host-bed radius, including outside manual zones. A selected zone counts containers within its X/Z circle, retaining all other container records.

PASS 2 registry and icons:

- `GET /api/registry` returns `{schemaVersion:1,gameVersion,source:{kind:'installed-assets'|'runtime-objectdb',exporter?,version?,method?},generatedAt,items,coverage,summary,categories}`. Without a manifest the items array is empty, coverage is unavailable and its percentage is `null`. A percentage measures `registered / definitionsFound` within the declared source scope. An installed asset export never claims runtime verification or coverage of loaded mods.
- The private local manifest is `localdata/registry/items.json`; backend reloads file changes while running. The icon directory is `localdata/icons/`. These game derived files and local overrides must stay out of the public repository.
- Each registry item is `{id:'prefab:'+prefab,prefab,prefabHash,nameRu,nameEn,category,subcategory,maxStack,iconKey?,source,metadata,diagnostics}`. `prefabHash` is the signed 32-bit Valheim `GetStableHashCode`. Display names never serve as IDs. Duplicate prefab IDs and incorrect hashes reject the complete manifest. Hash collisions retain both exact prefabs and refuse ambiguous `hash:<decimal>` aliases.
- `POST /api/registry` accepts a full registry manifest (up to 3 MiB), requires the same `X-VRM-Token` as ingest and persists it atomically. Coverage requires `definitionsFound >= registered`; `registered` is recomputed. `runtimeVerified` may only be true for a `runtime-objectdb` source. Diagnostic coverage counters and limitations are retained. `complete:true` also requires equal definition/registration counts and no invalid ObjectDB entries, duplicate IDs or unresolved references.
- `POST /api/icons/<64 lowercase SHA-256 hex>.png` requires `X-VRM-Token` and `Content-Type:image/png`. It accepts PNG bytes up to 512 KiB, validates PNG signature and dimensions (1–2048), and verifies the content hash matches the key. Existing content addressed files are immutable. `GET`/`HEAD` of the same route serves the local image with `image/png`; arbitrary filesystem paths are inaccessible.
- `PUT /api/registry/overrides` body `{prefab,category,subcategory?}` remains backward compatible and changes only local catalog presentation, never game definitions or inventory. Set `category:null` or `reset:true` to remove all overrides for this prefab. PASS 3 also accepts unknown exact prefab tokens, retaining them when a later registry export discovers the definition. Unsupported categories are rejected.
- Optional ingest item fields are `quality`, `variant` (nonnegative integers), `modId` (string), `metadata` and `customData` (objects up to 32 KiB). Send separate rows for distinct quality/variant/custom identities. The raw prefab token and each current stack quantity are retained. The state read enriches and combines unique hash aliases with exact prefabs, without rewriting the original stored tokens or accumulating totals across updates. `sourceIds` retains raw identifiers and `variants` retains quantity by instance metadata. Same display names do not merge different prefab IDs.
- The ingest response includes `reindexRequested:true` if any incoming prefab remains unknown. The plugin also periodically scans ObjectDB and reindexes when it encounters a missing prefab. Unknown records keep their identity, name and quantity; their category is `Неопознанные`. Registry reloads trigger the ordinary state-change/refetch flow, preserving frontend selection and filters.
- State `registry` summary includes `registered`, `definitionsFound`, `coveragePercent`, `scope`, `runtimeVerified`, `iconsFound`, `missingIcons`, `missingLocalization`, `unresolvedCategories`, `hashCollisions`, `loadError`, `generation`, `gameVersion`, `inventoryUnknownItems`, `reindexRequested`. A broken new manifest retains the last valid manifest and exposes `loadError`.
- Resource and container item metadata includes `id`, `nameRu`, `nameEn`, `prefabHash` when known, `iconUrl` (local `/api/icons/…` or null), `maxStack`, `subcategory`, `diagnostics`, `registryKnown`, `sourceIds`, `variants` and `searchText`. Resources additionally expose `availableQuantity=quantity`, `reservedQuantity=0`, `reservationsImplemented:false`. The application has no reservation operation; zero is descriptive and must not be presented as proof of a booking system.

Categories (in display order): `Древесина и растения`, `Камень и минералы`, `Руды и металлы`, `Строительные материалы`, `Сельское хозяйство`, `Сырые продукты`, `Приготовленная еда`, `Ингредиенты`, `Трофеи`, `Кожа, кости и ткани`, `Оружие`, `Броня`, `Инструменты`, `Боеприпасы`, `Зелья и расходники`, `Ценные предметы`, `Ключевые и специальные предметы`, `Прочее`. Automatic rules use prefab, ItemType and available metadata. `CATEGORY UNRESOLVED`, `MISSING LOCALIZATION`, `MISSING ICON`, `HASH COLLISION` and `UNKNOWN ITEM` are explicit diagnostics rather than hidden omissions.

PASS 3 logical clusters:

- Both `GET /api/state` and `GET /api/registry` include `clusters:[{id,name,system,categories:[{id,name}]}]`. These classify items independently of world-local physical storage `zones`. The stable system IDs are `construction`, `metallurgy`, `agriculture`, `food`, `alchemy`, `equipment`, `loot`, `valuables`, `unclassified`; system clusters cannot be renamed or deleted through this API. An empty inventory still includes the complete cluster definitions.
- Each registry definition, enriched container item and aggregated resource includes `clusterId`, `clusterName`, `clusterCategoryId`, `clusterCategory`, `classificationSource` and `tags:string[]`. Every row has exactly one primary cluster/category. Legacy `category` and `subcategory` remain unchanged. Classification sources are `manual`, `metadata`, `exact-prefab`, `exact-prefab-family`, `legacy-category`, `heuristic`, `unclassified`. Reliable ItemType/quest/drink/food/value metadata precedes automatic prefab rules; manual legacy category overrides also precede metadata. Translated names are never classifier keys. Known definitions lacking translations display their exact prefab rather than an obsolete raw hash label.
- `PUT /api/registry/overrides` body `{prefab,clusterId,clusterCategoryId}` assigns an existing system or custom category. `prefab` is the exact case-sensitive prefab identity, independently of language. A unique known `hash:<decimal>` canonicalizes to its prefab; an unresolved hash override survives reindexing and follows the definition only when the hash resolves uniquely. Collision aliases are never assigned to an arbitrary prefab. Existing legacy override fields are preserved when assigning a cluster. `{prefab,reset:true}` removes both legacy and cluster overrides for that item, including its unique raw-hash alias, and restores automatic classification. The response is `{ok:true,item,summary}`.
- `POST /api/clusters` body `{name}` creates a custom cluster and returns HTTP 201 `{ok:true,cluster,clusters}`. Its generated ID is `custom-<UUID>` and its initial category is `{id:'items',name:'Предметы'}`. Names are trimmed, nonempty, at most 80 characters, and unique without case distinctions. At most 100 custom clusters are supported.
- `PUT /api/clusters/<id>` body `{name}` renames a custom cluster without changing its ID or assignments and returns `{ok:true,cluster,clusters}`. Renaming a system cluster returns 403 `SYSTEM_CLUSTER`; an unknown ID returns 404. There is intentionally no delete endpoint, so assignments remain accessible.
- Custom definitions and overrides are stored atomically in private `localdata/registry/clusters.json` and `localdata/registry/overrides.json`, separately from `items.json`, the inventory databases and game saves. A successful ObjectDB reindex does not replace these settings. File changes are reloaded by the existing update loop. Invalid new configuration retains the last valid in-memory catalog and reports `registry.loadError`. HTTP edits notify both real and demo WebSocket subscribers through the existing `state-changed` event; no inventory or secret is broadcast in that event.
- State `registry` summary adds `classifiedItems`, `unclassifiedItems` and `manualClassifications`, all measured across the registered catalog, separately from `inventoryUnknownItems` and the retained legacy `unresolvedCategories`. `CLUSTER UNRESOLVED` marks an ambiguous or unknown primary cluster without deleting the resource. ObjectDB definitions include cosmetic/internal/NPC records and do not establish that every definition is obtainable.
- Resources add `statusCounts:{LIVE?:number,SNAPSHOT?:number,STALE?:number,OFFLINE?:number}` and `statusContainerIds:{LIVE?:string[],SNAPSHOT?:string[],STALE?:string[],OFFLINE?:string[]}` for the contributing containers, retaining the legacy least-current `status`. These reveal mixed states even when one resource combines live and snapshot observations.
- State `clusterStats:[{clusterId,uniqueItems,totalItems,containers,shortages,status,statusCounts}]` is computed exclusively from the selected world's already aggregated, zone-filtered resources. `uniqueItems` counts resource rows, including a configured minimum-only row at zero; `totalItems` sums current quantities once; `containers` is the union of contributing chest IDs; `shortages` counts rows with `quantity < minimum`. `statusCounts` uses a separate chest-ID union for each state, so a chest holding several items is counted once per cluster. Cluster chest counts cannot be summed into a global distinct-chest count. `status` is `MIXED` when more than one contributing source state exists and `EMPTY` when no contributing containers exist. It never labels a mixed aggregate LIVE. UI-level search, shortage/unknown and cluster filters may recompute the same summary over their filtered resource rows; grouping/collapse never changes the underlying totals.
