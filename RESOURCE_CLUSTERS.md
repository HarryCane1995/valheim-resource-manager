# Логические кластеры ресурсов — PASS 3

Кластеры отвечают на вопрос «для чего предмет», физические складские зоны — «где он находится». Они независимы. Иерархия **кластер → категория → prefab** не меняет игровой инвентарь, идентичность предметов, качество, варианты или сумму ресурсов.

## Системная структура

| ID | Кластер | Вложенные категории |
|---|---|---|
| construction | СТРОИТЕЛЬСТВО | Древесина; минералы; строительные компоненты; смолы, дёготь и вспомогательные материалы |
| metallurgy | МЕТАЛЛУРГИЯ | Руды; металлолом; обработанные металлы и сплавы; топливо и материалы обработки |
| agriculture | СЕЛЬСКОЕ ХОЗЯЙСТВО | Семена; урожай; растительное сырьё; сельскохозяйственные материалы |
| food | КУХНЯ И ПРОВИЗИЯ | Мясо и рыба; ягоды и грибы; ингредиенты; готовые блюда; прочие съедобные продукты |
| alchemy | АЛХИМИЯ И МАГИЯ | Зелья и медовуха; магические материалы; реагенты; расходники |
| equipment | СНАРЯЖЕНИЕ | Оружие; броня; инструменты; боеприпасы; аксессуары; служебные определения внешности |
| loot | ДОБЫЧА И ТРОФЕИ | Трофеи; шкуры; кости; прочие материалы существ |
| valuables | ЦЕННОСТИ И ОСОБЫЕ ПРЕДМЕТЫ | Монеты и сокровища; ключи; сюжетные и редкие специальные предметы |
| unclassified | НЕРАЗОБРАННОЕ | Неопознанные предметы; неоднозначные классификации; остальные предметы |

Каждое определение имеет ровно один `clusterId` и одну `clusterCategoryId`, включая fallback. Дополнительные `tags` не создают второй экземпляр ресурса. Старые `category` и `subcategory` сохранены для совместимости; категории новой иерархии находятся в отдельных полях `clusterCategoryId` / `clusterCategory`. Список старых категорий остаётся доступен в режиме группировки «Категории».

## Как выбирается классификация

Реализация: [server/clusters.mjs](server/clusters.mjs), применение и persistence: [server/registry.mjs](server/registry.mjs).

1. Ручное назначение по точному prefab ID, включая ранее сохранённую ручную legacy-категорию.
2. Надёжные игровые свойства: функциональный `ItemType`, `questItem`, `isDrink`, строительный инструмент и другие доступные метаданные.
3. Правила для точных prefab и ограниченных проверяемых семейств ID.
4. Совместимая исходная категория. Старый лексический вывод «броня» не принимается вопреки нативному типу `Material`.
5. Ограниченные эвристики для новых определений: например, суффиксы Ore, Scrap, Seeds. Отображаемое русское имя не является основанием.
6. Явное «Неразобранное» с диагностикой.

Широкий тип `Consumable` означает съедобность, но сам по себе не отличает урожай от кухонного запаса: точный prefab уточняет такие неоднозначности. Настоящее оружие с названием, содержащим Ore, остаётся оружием. Нелокализованные `Upgrader0..7Armor/Weapon` с типом Material остаются неоднозначными; совпадение слова Armor не превращает их в носимую броню.

Поле `classificationSource` показывает основание решения. Наличие кластера не доказывает, что предмет доступен игроку: ObjectDB включает атаки NPC, внешность и другие служебные определения. Атрибуция модам и игровой runtime остаются отдельными непроверенными областями.

## Ручные назначения и пользовательские кластеры

В существующей карточке ресурса раскройте **«Кластер и категория»**, выберите назначение и нажмите **«Назначить»**. **«Вернуть автоматическую»** удаляет ручные переопределения этого prefab. Настройки → **«Логические кластеры»** позволяет создать и переименовать собственную группу. ID пользовательского кластера стабилен и не меняется при переименовании. Его начальная категория — «Предметы». Системные группы защищены; операции удаления кластеров не предусмотрены.

Локальные файлы, целиком исключённые из Git:

- `localdata/registry/clusters.json` — пользовательские кластеры.
- `localdata/registry/overrides.json` — назначения по точным prefab ID.
- `localdata/registry/items.json` — независимо обновляемый реестр ObjectDB.

Переиндексация реестра не перезаписывает настройки. Старые hash-назначения разрешаются только при однозначном соответствии prefab; коллизии не объединяются. Неизвестный предмет сохраняет исходный ID и количество, остаётся видимым и тоже допускает ручное назначение.

API работает только на прежнем локальном сервере с проверкой Host/Origin:

```text
POST /api/clusters                          {name}
PUT  /api/clusters/:id                      {name}
PUT  /api/registry/overrides                {prefab, clusterId, clusterCategoryId}
PUT  /api/registry/overrides                {prefab, reset:true}
GET  /api/registry                         definitions + clusters + diagnostics
GET  /api/state?worldId=...&zoneId=...       selected inventory + clusters + clusterStats
```

Для изменений требуется `Content-Type: application/json`. Создание возвращает HTTP 201, переименование и назначение — HTTP 200. Категорию назначения выбирают по стабильному `id` из `clusters[].categories`, а не по русскому имени. Переименование системного кластера возвращает 403; некорректная пара кластер/категория — 400. Название пользовательской группы содержит 1–80 символов после обрезки внешних пробелов; поддерживается до 100 групп. Удаление и переименование системных групп не меняют доступность предметов, поскольку такие операции API отклоняет. Полный контракт — в [shared/contract.md](shared/contract.md).

## Интерфейс и аналитика

NORMAL использует карточки кластеров с раскрытием категорий и предметов; предмет открывает прежнюю панель сундуков. COMPACT по умолчанию группируется по кластерам, поддерживает категории и плоский список, отдельное сворачивание уровней, выбор столбцов, плотность и фокус второго монитора. Глобальный поиск временно раскрывает родителей результата, сохраняя прежние настройки сворачивания.

Поиск, кластер, дефицит/неопознанные и физическая зона комбинируются. Оба режима используют одну уже агрегированную выборку и общие функции из [src/clusters.ts](src/clusters.ts). Количества суммируются по ресурсам, сундуки считаются через объединение их ID. Количества разных миров не складываются. При зоне используется уже ограниченная этой зоной выборка.

Статусы контейнеров сохраняются в `statusContainerIds`; повторяющийся сундук внутри кластера не увеличивает число источников. Смесь LIVE/STALE/OFFLINE/SNAPSHOT обозначается MIXED с деталями, а не достоверным общим live-остатком. Пустая группа не считается LIVE. При WebSocket-обновлении сохраняются поиск, группы и прокрутка; memo строк COMPACT пропускает неизменившееся отображаемое содержимое. Это оптимизация UI, а не гарантия игровой задержки.

`/api/state.clusterStats` содержит сводки выбранного мира и зоны до дополнительных фильтров интерфейса. NORMAL и COMPACT пересчитывают отображаемые сводки по общей отфильтрованной выборке. `uniqueItems` считает строки ресурсов, включая отсутствующий предмет с настроенным минимальным запасом; такая строка имеет количество 0 и может создавать дефицит. Число сундуков и счётчики статусов используют объединения ID, а не число строк или стеков. Поэтому суммы количества складываются между кластерами, а суммировать количество сундуков разных кластеров нельзя: один сундук может содержать предметы нескольких групп.

Поля `registry.classifiedItems`, `registry.unclassifiedItems` и `registry.manualClassifications` относятся ко всему зарегистрированному каталогу. `registry.inventoryUnknownItems` относится к текущей выборке инвентаря. Сохранённое `registry.unresolvedCategories` описывает старую плоскую классификацию и не заменяет новый счётчик «Неразобранного».

Снимок содержит 151 уникальный сундук. Для «Металлургии» подтверждено 10 типов, 788 единиц в 18 сундуках, со статусом SNAPSHOT. Эти числа описывают сохранённые наблюдения, а не текущий live-остаток игры.

18 неоднозначных определений: 16 вариантов `Upgrader0..7Armor/Weapon`, `GenericMoldUncooked`, `LastBossGate_RuneTile`. Они имеют собственную идентичность и не исчезают. Все прежние 29 позиций legacy-«Прочее» наблюдавшегося инвентаря получили содержательную классификацию; новые 10 неоднозначных относятся к исправлению прежних лексических догадок.

В прежних 210 `CATEGORY UNRESOLVED` обнаружены 114 записей типа `Customization`, 85 `Material` и 11 `Misc`. Для 114 классификация основана на нативном функциональном типе, для 73 — на точном prefab, для 22 — на ограниченном семействе prefab. Оставшаяся `LastBossGate_RuneTile` не получила выдуманного назначения. Все 114 определений внешности отнесены к отдельной служебной категории; они не объявляются добываемыми ресурсами. Число 1501 отражает наличие содержательного правила, а не независимо доказанную безошибочность каждой смысловой категории.

Связь всех 271 типов снимка с настоящими локальными пиктограммами сохранена. 1519/1522 = 99,80% остаётся показателем **статического покрытия исходного ObjectDB**, а не процентом правильной классификации или runtime-полноты.
