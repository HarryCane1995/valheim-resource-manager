# Valheim Resource Manager

Локальная панель учёта ресурсов Valheim с русским интерфейсом: C#-плагин BepInEx → HTTP API → SQLite → WebSocket → React. Данные мира читаются; метки сундуков, зоны и минимальные запасы сохраняются отдельно от игры.

## Portable-приложение Windows

Для передачи другому игроку достаточно **одного EXE со встроенным плагином**. У получателя уже должны быть Valheim 1.0.20 и BepInEx. Приложение находит папку игры через Steam, добавляет собственную DLL и автоматически создаёт локальную связь. Ручного копирования плагина и токенов не требуется. [Первый запуск и проверка](SHARING.md).

Запустите **`ValheimResourceManager.exe`** двойным щелчком. Установщик, CMD, отдельные Node.js, Python и браузер для готового EXE не нужны. Приложение открывает собственное окно и запускает HTTP/WebSocket/SQLite внутри своего процесса. **F11** или кнопка «Полный экран» разворачивает окно на весь экран; **Esc** возвращает обычное окно. Повторный запуск показывает уже открытое окно.

EXE создаёт `data/` и `localdata/` рядом с собой; храните его в доступной для записи отдельной папке. В этом проекте EXE рядом с прежними папками автоматически использует существующие базы, токен, иконки и настройки. Чтобы перенести свою установку, закройте панель и переносите EXE вместе с этими приватными папками. Сам EXE не содержит ваших данных или игровых ассетов. Chromium временно распаковывается в Windows Temp; профиль браузера хранится в `data/desktop-profile/`. Регистрация в системе и автозапуск Windows не требуются. Для первого подключения нужны права записи в существующую папку игры. Файл не подписан сертификатом издателя.

Приложение определяет наличие `valheim.exe`. Загруженный мир определяется по UID, который передаёт установленный плагин: режим **«Авто: активный мир»** следует за подключённым миром, а ручной выбор фиксирует его. После выхода из игры последние остатки остаются доступны с прежними статусами свежести. При обычном запуске и закрытии EXE внутренний сервер запускается и завершается автоматически. Если уже работает совместимая отдельная панель, EXE подключается к ней; её процесс ему не принадлежит и при закрытии EXE не останавливается.

Для резервного режима нажмите **«Выбрать сохранение»** и укажите папку мира либо `worlds_local`. При нескольких мирах приложение предлагает выбрать один. Оно следит только за завершёнными поколениями поддерживаемого chunk-формата Valheim **1.0.20** и показывает **SNAPSHOT**, а не live-данные. Старые монолитные `.db` и незагруженные облачные файлы не поддерживаются. Автоматически выбирать «самый новый файл» оно не будет: это не подтверждает, какой мир открыт в игре. Прежняя настройка `data/snapshot-source.json` подхватывается автоматически. При чтении snapshot файлы сохранения не изменяются.

**Первое подключение:** закройте Valheim обычным способом. Приложение добавит собственную DLL/CFG в существующий BepInEx и затем запустит игру, если включено «Запускать игру вместе с приложением». Дальше достаточно двойного щелчка по EXE. Неизвестные существующие файлы не заменяются; другие моды и загрузчик сохраняются. При нескольких установках или нестандартном пути доступна кнопка «Папка игры».

**Ограничения:** BepInEx должен быть установлен заранее. Поддерживается исследованная игровая DLL Valheim 1.0.20; другая версия отклоняется. Профили отдельных мод-менеджеров вне папки игры автоматически не подключаются. Заполненные локальные токены остаются на своём ПК. Snapshot имеет частичный охват и сохраняет прежние сундуки при их отсутствии в следующем снимке до live-подтверждения; качество/варианты из snapshot отдельно не восстанавливаются. Пакет ограничен 3 МиБ и 5000 контейнерами. Полнота мира и игровая задержка не гарантируются. Другие ограничения и результаты — в [TEST_REPORT.md](TEST_REPORT.md).

Сборка EXE из публичных исходников (Node.js 24+, .NET SDK, установленная Valheim с BepInEx, Windows x64 и интернет для загрузки Electron/NSIS):

```powershell
npm.cmd ci
node node_modules/electron/install.js
npm.cmd run desktop:pack
```

Результат — `ValheimResourceManager.exe` в корне и версия в `output/desktop/build-*/`. Во время разработки после `npm.cmd run build` доступен `npm.cmd run desktop:dev`. Упаковщик собирает нашу DLL без отладочных путей и включает её в EXE. Для нестандартного пути сборки задайте `VRM_GAME_DIRECTORY`. Используются явный список исходников, собранный frontend, `ws` и открытый runtime Electron; базы, извлечённые иконки и игровые DLL в него не входят.

**Закрытие меню.** Щелчок по основному интерфейсу закрывает карточку предмета; другой предмет открывается сразу этим же щелчком. Выпадающие меню столбцов, вариантов, классификации и дополнительных позиций сундука закрываются при щелчке снаружи. Внутренние поля и галочки остаются доступны. Esc закрывает сначала вложенное меню, затем панель; помощь и редактор зоны тоже поддерживают закрытие снаружи и по Esc. Раскрытые кластеры и категории сохраняют своё состояние.

**Минимальный запас и цветная шкала.** Для текущего мира установлен общий минимум **200 единиц**. Новые обнаруженные ресурсы наследуют его; индивидуальный порог можно изменить в карточке, включая 0 для отключения предупреждений. Ранее обнаруженный израсходованный ресурс остаётся в каталоге как `0 / 200`. Пустые записи всего игрового справочника автоматически не добавляются.

- **Красный:** меньше минимума — при пороге 200 это 0–199.
- **Жёлтый:** минимум достигнут, запас меньше 25% — 200–249.
- **Зелёный:** запас от 25% над минимумом — 250 и больше.

Шкалы есть в NORMAL-кластерах, карточках, таблице, COMPACT с одной/двумя колонками и карточке предмета. Отметка минимума расположена на 80% шкалы; полный диапазон соответствует минимуму +25%. Цвет оценивает последние известные остатки выбранной области, а статус LIVE/STALE/OFFLINE/SNAPSHOT отдельно показывает свежесть данных. Пороги общие для мира; выбранная зона и радиус 500 м меняют количества.

**Учёт в радиусе 500 м от кровати хоста.** Новый плагин читает сохранённую точку выбранной кровати для текущего мира. После её получения backend ограничивает все остатки, кластеры и списки сундуков кругом X/Z с радиусом 500 м; складские зоны дополнительно сужают эту область. При новой привязке к кровати центр переносится. Записи вне круга сохраняются в локальной базе. Если хост явно сообщает об отсутствии выбранной кровати, учёт приостанавливается.

Для ручного обновления плагина при работе из исходников закройте Valheim обычным способом, запустите `UPDATE-GAME-PLUGIN.cmd`, убедитесь в результате `UPDATED` или `REPAIRED` и снова запустите игру. Скрипт проверяет квитанцию установки и сохраняет конфигурацию; при работающей игре возвращает `DEFERRED`, без замены DLL. Desktop-приложение само добавляет отсутствующий плагин, а совместимую установленную DLL сохраняет. Новая сборка загружается при следующем обычном запуске игры. До первого сообщения с точкой панель показывает прежний охват и явное предупреждение, что радиус ещё не применяется. Сохранённая точка не удостоверяет существование кровати сейчас; dedicated server и удалённый клиент не получают точку кровати владельца автоматически. Координаты остаются локальными; карту добавлять не требуется.

Обновлятор также восстанавливает отсутствующую собственную DLL по проверенной квитанции: результат `REPAIRED` означает успешное восстановление. Он сохраняет CFG байт-в-байт; изменение комментариев и форматирования BepInEx допускается только при совпадении всех ключей и значений с резервной копией, SHA-256 которой указан в квитанции. Изменённые значения, неизвестные/повторные ключи, отсутствующий CFG или неподдерживаемая игровая DLL останавливают обновление с конкретной причиной. Неизвестные существующие DLL не заменяются.

**Исправление иконок — 17.10.2026.** Runtime-манифест мог ссылаться на PNG, которые не были доставлены. Backend теперь использует последнюю доступную настоящую иконку только для точного prefab и той же версии игры, включая приватный статический экспорт; интерфейс ограниченно повторяет загрузку видимых изображений. В реальной HTTP-проверке доступны и декодируются **296/296** иконок текущих типов ресурсов; SHA-256 каждого файла совпал с URL. Игровые PNG и кеш остаются вне Git. Новая C#-реализация публикует манифест только после доставки всех PNG; она собрана и проверена автоматически, а её работа внутри игры остаётся **UNVERIFIED**. Подробности и разделение реальных проверок и симуляций — в [TEST_REPORT.md](TEST_REPORT.md). Числа snapshot в описании PASS 3 ниже относятся к предыдущему этапу.

**Статус: рабочий MVP 0.3.0, PASS 3.** Добавлена иерархия **кластер → категория → предмет**, ручные назначения и пользовательские группы. Содержательно классифицировано **1501 из 1519** определений; **18** явно остаются в «Неразобранном». Все 1519 имеют один основной путь, включая fallback. Проверены 1519 определений из 1522 записей сериализованного ObjectDB (**99,80% статического покрытия**); все **271** тип предметов текущего снимка базы распознаны и имеют иконки. Полнота runtime и модов **UNVERIFIED**. Сборщик C# остаётся 0.2.0; его выполнение внутри игры и сценарий «положил 40 дерева → увидел +40» ещё не проверены, игровая задержка не измерена.

## Категории ChestSorter

Вкладка **ChestSorter** показывает весь доступный реестр предметов по правилам установленного [ChestSorter](https://thunderstore.io/c/valheim/p/Heyaeyaeya/ChestSorter/), включая спойлерные и ещё не встречавшиеся в учёте определения. Названия, порядок, исключения и связи категорий читаются из `BepInEx/config/ChestSorter.categories.txt` выбранной установки игры. У текущего мода 52 категории; свои изменения файла подхватываются при очередном обновлении панели. Поиск работает по предметам и категориям; доступны фильтр дефицита, сортировка, одна/две колонки, сворачивание и показ пустых категорий. Выбор родительской Food включает её дочерние категории. Нажатие открывает карточку предмета; сведения о сундуках и пороге показываются для отслеживаемых остатков.

**Красный текст и пометка «НОВЫЙ»** означают, что менеджер ещё не встречал предмет в учёте выбранного мира. История сохраняется после расхода, уничтожения сундука и смены зоны/области 500 м; в другом мире она независима. Это история локального менеджера, включая ранее назначенные пороги, а не список открытых рецептов или материалов персонажа. Предметы, которые игрок брал до подключения менеджера либо не передавал источнику, могут оставаться новыми.

У справочных предметов без учёта остатков стоит **«—»** и нет шкалы дефицита. Они не добавляют нулевые запасы, пороги 200 или нехватку в обзор ресурсов и другие вкладки. Ранее учтённый израсходованный ресурс сохраняет обычное `0 / 200`. На 18.10.2026 доступно **1519 распознанных определений из 1522 записей ObjectDB**; три неразрешённые записи не выдумываются. Полный реестр включает служебные предметы/атаки NPC: это не число добываемых ресурсов. Для части служебных определений нет иконки или перевода; показывается исходный prefab и буквенная заглушка.

Остатки, мир, складская зона и радиус 500 м берутся из той же базы, что обзор ресурсов. Каждый предмет входит ровно в одну категорию; родительские фильтры не удваивают количества. Правила определяются по точному prefab и игровым метаданным, включая пищевые свойства. Недостаточные данные явно остаются без назначения. При отсутствии или ошибке файла ресурсы сохраняются в списке. Файлы мода и игровой мир не изменяются; реальные Push/Sort выполняются в игре. Эта вкладка не читает сохранённые на сундуках теги назначения, предметные теги и группы ChestSorter, поэтому не предсказывает конкретный сундук назначения.

Для EXE путь берётся из выбранной папки игры, для запуска backend из исходников — из приватного `data/desktop-game.json`, созданного приложением. Чужая DLL, исходники мода, правила конкретной установки и данные игрока в дистрибутив не добавляются. Детали и результаты сравнения с исходным классификатором — в [ARCHITECTURE.md](ARCHITECTURE.md) и [TEST_REPORT.md](TEST_REPORT.md).

Рядом с названием каждой категории есть ручной чекбокс **«Сундук настроен»**. Отметки сохраняются на этом компьютере отдельно для каждого мира и не зависят от выбранной складской зоны. Их можно менять и у свёрнутой категории; чтобы отметить категории без ресурсов, включите «Пустые категории». Это ваша пометка о настройке — автоматической проверки тегов сундука она не выполняет.

## Логические кластеры

Девять системных групп: **Строительство, Металлургия, Сельское хозяйство, Кухня и провизия, Алхимия и магия, Снаряжение, Добыча и трофеи, Ценности и особые предметы, Неразобранное**. NORMAL показывает карточки с итогами, дефицитами, уникальными сундуками и состоянием данных. Раскройте кластер и категорию, чтобы выбрать предмет и открыть прежнюю панель сундуков.

В COMPACT доступна группировка **Кластеры / Категории / Без группировки**; по умолчанию — кластеры. Уровни сворачиваются отдельно, настройки и прокрутка сохраняются. Глобальный поиск показывает результаты даже внутри свёрнутых групп, временно раскрывая родителей. Поиск, дефицит, неопознанные предметы, кластер и физическая складская зона комбинируются. Смешанные состояния источников явно обозначаются.

Переключатель **«Колонки: 1 / 2»** в COMPACT распределяет ресурсы между двумя таблицами с независимой прокруткой и закреплёнными заголовками. Предметы не дублируются; итоги группы относятся к своей колонке. В NORMAL настройка **«Столбцы: Авто / 1 / 2»** управляет сеткой обзора кластеров; на телефоне сетка становится одноколоночной. Оба выбора сохраняются независимо в браузере.

В карточке предмета раскройте **«Кластер и категория»** для ручного назначения или возврата автоматической классификации. Собственные кластеры создаются и переименовываются в настройках. Назначения по точному prefab ID хранятся отдельно от ObjectDB и переживают переиндексацию. Складские зоны по-прежнему описывают местоположение, независимо от кластеров.

Из прежних 210 определений «Прочее» содержательно классифицировано 209; все 29 встречавшихся в snapshot получили группы. Одновременно 10 других позиций снимка честно перенесены в неоднозначные: это нелокализованные Material-определения Upgrader, которые нельзя считать бронёй или оружием только по имени. Полные правила и распределение: [RESOURCE_CLUSTERS.md](RESOURCE_CLUSTERS.md).

## Компактный режим и игровые пиктограммы

Переключатель **NORMAL / COMPACT** работает без перезагрузки. COMPACT показывает восемь столбцов: иконку, название, количество, доступный остаток, резерв, сундуки, зону и статус. Высота строки регулируется: 30/32/34/40 px. Есть закреплённая шапка, сортировка, поиск RU/EN/prefab/ID/hash, категории со сворачиванием, выбор столбцов и правая панель мест хранения. **Фокус** скрывает навигацию, крупные заголовки и второстепенные панели; проверены окна 800–1200 px. Режим, плотность и настройки сохраняются локально; обновления сохраняют поиск, сортировку, выбранный предмет и прокрутку. Резервирование не реализовано: прочерк в столбце резерва означает отсутствие учёта резервов.

Для получения локального каталога и настоящих изображений выполните [инструкцию ValheimIconExporter](tools/ValheimIconExporter/README.md). Он читает собственную установленную игру, экспортирует `localdata/registry/items.json` и `localdata/icons/<sha256>.png`. Backend автоматически подхватывает новый манифест. Плагин 0.2 также содержит [runtime-экспортёр ObjectDB и Sprite](tools/registry-runtime/README.md), который сможет учесть определения модов после следующего обычного запуска игры. Подключение новой DLL к уже работающей игре не производится.

Локально получены **1075 вариантов иконок / 969 уникальных PNG**, покрывающих **994 определения**. У остальных 525 записей реестра пиктограмма не задана, включая внутренние определения; происхождение каждой записи индивидуально не удостоверено. Используется нейтральное сокращение названия. PNG и извлечённый каталог исключены из Git: публично доступны экспортёры, формат и инструкции. Прав на распространение игровых изображений проект не заявляет. Подробные счётчики и ограничения: [ITEM_REGISTRY.md](ITEM_REGISTRY.md), [ICON_COVERAGE_REPORT.md](ICON_COVERAGE_REPORT.md).

## Возможности

- Каталог ресурсов: поиск, категории, сортировка, карточки и таблица.
- Карточка ресурса с количеством в каждом известном сундуке, координатами XYZ и временем наблюдения.
- Локальные названия сундуков, круговые складские зоны X/Z, минимальные запасы и дефициты.
- Сохранение последних остатков при отключении источника или выгрузке сундука.
- Раздельные статусы `LIVE`, `STALE`, `OFFLINE`, `SNAPSHOT` и явное обозначение частичного охвата.
- Изолированное демо: добавление 40 дерева, перенос, отключение и восстановление.
- Дополнительное чтение завершённых сохранений поддерживаемого формата без записи в игровые файлы.

Движущиеся контейнеры, транспорт, надгробия и инвентарь игрока исключены из live-сборщика. Полный охват мира не обещается. Движка рецептов и планирования крафта пока нет.

## Требования

Для панели:

- Windows и PowerShell 5.1 для `.cmd`/`.ps1` помощников.
- Node.js **24 или новее** с npm: backend использует встроенный `node:sqlite`.
- Современный браузер. При первой установке зависимостей нужен интернет.

Для подключения игры:

- Собственная установленная Valheim. Исследованная версия — **1.0.20**; плагин отклоняет другие версии.
- Уже установленный BepInEx. Проверенная локальная сборка использовала **5.4.23.5** и Harmony из этой установки.
- .NET SDK для сборки C#; проверена сборка SDK **9.0.200**, target `netstandard2.1`, ссылки берутся из локальной игры и BepInEx.
- Установщик дополнительно проверяет точный SHA256 исследованной `assembly_valheim.dll`. Совпадения номера версии недостаточно: неподтверждённая DLL будет отклонена.

Python **3.11+** нужен только для snapshot-парсера и его тестов. Репозиторий не содержит Valheim/Unity/BepInEx/Harmony DLL, игровых ассетов, сохранений, рабочих баз и токенов. Библиотеки для сборки нужно получить в своей установленной игре; проект не скачивает и не переустанавливает их.

## Установка и запуск панели

```powershell
git clone https://github.com/HarryCane1995/valheim-resource-manager.git
cd valheim-resource-manager
npm.cmd ci
npm.cmd run build
npm.cmd start
```

Откройте [http://127.0.0.1:37841](http://127.0.0.1:37841). Backend создаст `data/live.sqlite`, отдельную `data/demo.sqlite` и приватный `data/ingest-token.txt`. В свежем клоне реальная база пуста. Демо включается явной кнопкой в интерфейсе и не записывает данные в реальную базу.

В Windows также можно запустить **START-RESOURCE-MANAGER.cmd**: помощник установит зависимости при отсутствии `node_modules`, соберёт интерфейс, запустит backend в фоне и откроет браузер. **STOP-RESOURCE-MANAGER.cmd** останавливает только собственные процессы backend/watcher с проверкой командной строки. Игру помощники не закрывают.

При запуске через `npm.cmd start` остановка — `Ctrl+C` в том же терминале. Порт `37841` должен быть свободен. Обычный запуск обслуживает production build из `dist/`.

Для разработки оставьте backend работающим и выполните `npm.cmd run dev`; откройте Vite-панель на `http://127.0.0.1:5173`. Proxy поддерживает HTTP и WebSocket: он заменяет Origin на адрес backend только при точном совпадении входного Origin с loopback Host (`127.0.0.1` или `localhost`) с допустимым портом. Посторонний Origin сохраняется и отклоняется backend с `403`. Строгая политика доступа backend не ослаблена; этот путь проверен отдельным изолированным интеграционным тестом.

## Подключение к Valheim

1. Запустите панель, чтобы backend создал локальный токен.
2. Соберите **собственный** плагин по своей установке:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\plugin\build.ps1 -GameDirectory "C:\Program Files (x86)\Steam\steamapps\common\Valheim"
   ```

   При другом расположении замените значение `-GameDirectory`. Результат: `plugin/bin/Release/netstandard2.1/ValheimResourceManager.dll`. Сборка сама не изменяет игру. Два известных предупреждения MSB3277 о Unity facade описаны в [TEST_REPORT.md](TEST_REPORT.md).

3. Установите плагин и его собственную конфигурацию:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-plugin.ps1 -GameDirectory "C:\Program Files (x86)\Steam\steamapps\common\Valheim"
   ```

   **INSTALL-GAME-PLUGIN.cmd** вызывает тот же установщик для стандартного пути Steam. Установщик проверяет игровую DLL, наличие BepInEx и отсутствие чужих файлов по целевым путям. Он добавляет только собственную DLL и `BepInEx/config/local.valheimresourcemanager.cfg`, переносит токен локально без его вывода и сохраняет квитанцию в `data/`. При несовпадении сборки или уже существующем чужом файле установка останавливается.

4. При следующем обычном запуске Valheim BepInEx загрузит плагин. Копирование DLL не загружает её в уже работающую игру. Оставьте backend работающим, загрузите мир и подойдите к базе. В локальном BepInEx-журнале ожидаются `Read-only integration ready` и `Observing world`.
5. Проверьте игровой источник и статусы в панели. В разделе складских зон задайте реальный центр X/Z и радиус базы: первоначальная зона радиусом 100 м — только редактируемое предложение вокруг первого наблюдения.
6. Выполните ручную проверку: положите ровно 40 дерева в поддерживаемый сундук, проверьте +40 и правильное место хранения, затем изъятие/перенос и уход с базы. До выполнения этого сценария live-критерий остаётся неподтверждённым.

Плагин отправляет данные только на loopback HTTP и требует локальный `X-VRM-Token`. Пример структуры конфигурации: [plugin/local.valheimresourcemanager.cfg.example](plugin/local.valheimresourcemanager.cfg.example). Не публикуйте заполненный CFG, токен, журналы игры и `data/`.

### Удаление и обновление плагина

**UNINSTALL-GAME-PLUGIN.cmd** использует локальный manifest и независимую квитанцию. Он удаляет только добавленные этим установщиком DLL/CFG с совпадающими хешами. Изменённые и чужие файлы сохраняются. Уже загруженный плагин останется в памяти до обычного закрытия игры.

Для обновления собственной зарегистрированной установки после сборки выполните `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/update-plugin.ps1`. Скрипт проверяет квитанции, хеши и отсутствие процесса Valheim, создаёт приватную резервную копию и заменяет только собственную DLL. CFG с токеном и SourceId сохраняется побайтно. При работающей игре возвращается `DEFERRED`, изменённые DLL/CFG сохраняются; новый плагин загрузится при следующем обычном запуске. После обновления самой Valheim требуется новый аудит API/формата: не обходите проверку версии или SHA256 ради установки.

## Резервное чтение сохранений

Snapshot — отдельный источник; он отражает **сохранение мира**, а не мгновенное перекладывание предметов. Поддерживаются только исследованные chunk-форматы 40–42, inventory 108–110 и согласованное завершённое поколение `_main.N.ok` с mapping/metadata/chunk файлами. Старые монолитные `.db` и произвольные будущие форматы не поддерживаются.

Однократное чтение и импорт, с подстановкой своего каталога завершённого сохранения:

```powershell
python .\scripts\read_snapshot.py --world-folder "C:\path\to\completed-world-folder" --output ".\output\private-snapshot-check" --import-url "http://127.0.0.1:37841/api/snapshot" --token-file ".\data\ingest-token.txt"
```

Каталог `--output` должен быть новым. CLI сохраняет там manifest, payload **и копии входных файлов** для проверки; это приватные данные, исключённые из Git. Входные игровые файлы открываются только для чтения, хешируются и повторно проверяются перед импортом. Поля истории игроков отбрасываются парсером, но исходные файлы всё равно являются приватными.

Для watcher вручную создайте приватный `data/snapshot-source.json`:

```json
{
  "worldFolder": "C:\\path\\to\\completed-world-folder",
  "worldId": "YOUR_WORLD_UID_AS_STRING"
}
```

Укажите настоящий UID из локального snapshot manifest строкой. После этого запустите `python .\scripts\watch_snapshot.py` либо заново запустите Windows-помощник панели. Watcher проверяет новые завершённые поколения каждые 5 секунд, пропускает тяжёлое чтение при активном live-источнике и сохраняет payload/manifest без копирования всех чанков. Сейчас он рассчитан на один настроенный каталог/мир; автоматического выбора мира и мастера настройки нет. Переход watcher на следующее **реальное** поколение ещё не подтверждён игровым тестом.

## Актуальность и ограничения

| Статус | Значение |
|---|---|
| `LIVE` | Активный источник подтвердил этот контейнер в текущем сеансе не более 15 секунд назад |
| `STALE` | Источник активен, но наблюдение контейнера старше или относится к предыдущему сеансу |
| `OFFLINE` | Контакт с источником отсутствует более 12 секунд; последние остатки сохранены |
| `SNAPSHOT` | Данные получены из завершённого сохранения; runtime ZDOID не подтверждён |

Heartbeat сам по себе не обновляет время содержимого выгруженного сундука. Отсутствие сундука в пакете не означает уничтожение: остатки исключаются только при явном подтверждении уничтожения. Охват штатных сборщиков остаётся `partial`, включая host/server.

В исследованном сохранении runtime ZDOID пересоздаётся при загрузке. Для неподвижных сундуков используется локальный ключ из UID мира, prefab hash и точных float32-битов XYZ; настоящий runtime ZDOID хранится отдельно строкой. Перемещение сундука меняет этот ключ, а совпадающие prefab и точные координаты создают конфликт. Неизвестные prefab-хеши сохраняются без догадок о названии.

В последнем приватном снимке parser → SQLite → UI учтены **151** распознанный сундук, **271** тип предметов и **21 402** единицы. Количество до и после разрешения hash через реестр совпало, отдельно проверен каждый сундук. Это частичный snapshot, а не независимая проверка сундуков внутри игры. Исходный мир, координаты, его идентификаторы и скриншоты с реальными данными не поставляются. Подробности и оставшиеся проверки — в [TEST_REPORT.md](TEST_REPORT.md), устройство системы — в [ARCHITECTURE.md](ARCHITECTURE.md).
